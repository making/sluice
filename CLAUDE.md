# sluice

TCP tunnel over a single gRPC bidirectional stream; the HTTP reverse proxy is its first consumer.

## Layout

Maven multi-module. Build + test with `./mvnw verify` (JDK 25, a Rust toolchain, `cc` and `protoc`
required: `sluice-client` builds `sluice-client-wasm` and `sluice-it` `sluice-flume` with cargo). Always run
the reactor build from the root: `./mvnw -pl <module>` resolves the other modules from
stale `~/.m2` snapshots and fails with misleading `NoSuchMethodError`s.

- `sluice-proto`: proto + generated stubs + shared tunnel machinery (`am.ik.sluice.tunnel`: VirtualConnection / SessionSender / StreamRelay) + the HTTP/1.1 parsers the server's relay and the client's filters share (`am.ik.sluice.http1`)
- `sluice-server`: gRPC control plane (8001) + raw TCP data plane (`sluice.data-port`, 8000) + actuator and management console `/console` (8081)
- `sluice-client`: tunnel client. grpc:// / grpcs:// (TLS verification skip via `sluice.insecure`). Filters per route on its HTTP/1.1 connections (`.kb/client-filters.md`): built-ins and a custom build's factories in Java on `UpstreamFilter` (the maintainer's way: far cheaper), users' proxy-wasm plugins compiled by wasmtime in `sluice-client-wasm` (`proxy-wasm-plugins.md`), loaded through FFM (`Wasmtime`; on a native image its calls per call go through C function pointers, `src/native/java`). The test plugins' binaries are in `src/test/resources/wasm`: `src/test/guest/build.sh` rebuilds them
- `sluice-client-wasm` (Rust, own Cargo workspace): the library sluice-client runs its plugins with, a cdylib on wasmtime (copying collector), its C ABI of plain scalars and pointers (`src/lib.rs`): one budget for a VM's memories, GC heap and tables, epoch deadlines, every import through one callback, no panic past it. sluice-client's build compiles it (release) and carries it as a resource per platform (`META-INF/native/<os>-<arch>/`), extracted when a plugin is first defined. Gates as sluice-flume's
- `sluice-it`: full stack E2E tests (real server + client apps in one JVM); E2E tests live here, not in the app modules
- `sluice-flume` (Rust, own Cargo workspace): the live access log's collector; nodes and wickets feed it, consoles and the cf-api watch it (`flume.proto`), and exports them over OTLP/HTTP when configured. Gates: `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test`
- `sluice-wicket-runtime-wasi` (Rust, own Cargo workspace, laid out as sluice-flume): a tunnel client serving each route with a wasi:http component (wasmtime); its guest `examples/` are a separate workspace on a pinned nightly. Same gates; its tests run `redis-server` (with TLS) as a child process, and sluice-wicket-keyvalue-gemfire's mock cluster in process
- `sluice-wicket-site` (Rust, own Cargo workspace on the nightly the wicket's `examples/` pin, wasm32-wasip3): the static site's wasi:http component, serving the files its route preopens read-only (`files=`); sluice-wicket-cf-api embeds it, the wicket's tests build it. Gates: `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`
- `sluice-wicket-cf-api` (Rust, own Cargo workspace, laid out as sluice-flume): a Cloud Foundry API facade (CC v3 / UAA / log-cache, the subset the OSS `cf` CLI v8 uses) deploying apps to the wickets it names (`--wicket`, repeated; wasi and Firecracker ones together) through their app API, an app's instances spread by room over those of its droplet's stack (`placement.rs`; what is pushed decides the stack: `staging.rs`), each wicket told by the id its listing names; a static site (a package with an `index.html`) as `sluice-wicket-site`, which its build embeds (`build.rs`: on the nightly it pins, or `SLUICE_WICKET_SITE_WASM`), with the files a tar the wicket preopens read-only; its state in `--data-dir`'s `state.json` or, with `--state`, in PostgreSQL (`postgres.rs`: a row per entity, `records.rs`, and beside them the logins' tables, `uaa.rs`; its tests run a `postgres:18-alpine` container, else the one `SLUICE_CF_API_TEST_POSTGRES` names), the packages and droplets (`blobs.rs`) in it too or, with `--blobs`, in an S3 bucket (`s3.rs`; a `rustfs/rustfs` container, else `SLUICE_CF_API_TEST_S3`), one the state names no more swept (`Store::sweep`: a droplet is named only where no sweep began since its blobs were seen), what several instances share documented in its `ha.md`, not its README, one at a time reconciling the wickets (`lease.rs`: a lease in the store, a turn's writes fenced by its epoch at the wickets; what it saw of them kept for every instance), the edits the wickets take at once made by that one, the others sending them to its `--instance-url` (`api.rs`: `edit`), the work outliving a request (a build, a broker's operation, an app's delete after its unbinds) that one's turn's too, taken up from the state (`Controller::follow`, each change `Store::lead`), the logs one on every instance through the flume (`logs.rs`, `flume.rs`: its own lines fed to it, a line's timestamp the flume's), an update's two builds and flags on one store (`instances.rs`: the oldest build leads, the topology the store's; `postgres::SCHEMA`, moved with what an older build would undo; a row's fields a build does not read kept, `records.rs`); source staged by a Cloud Native Buildpacks builder (`--cnb-builder`) on a Firecracker wicket, the droplet a tar it keeps. Same gates; its integration test runs the OSS CLI (`SLUICE_CF_CLI`, else `cf8` on the PATH; CI installs 8.19.0) against two instances of the cf-api on one PostgreSQL and one bucket (containers, as its store's tests'), each request to the next through the test's relay (`tests/relay`), begun as a previous build (`SLUICE_CF_API_PREVIOUS`, else on Linux the image `PREVIOUS_IMAGE` pins) and updated one at a time, and two wickets it builds from `sluice-wicket-runtime-wasi`, on a flume it builds from `sluice-flume`, and where `/dev/kvm` is usable (`sg kvm -c 'cargo test'`) from `sluice-wicket-runtime-firecracker` (a build with the lifecycle of `SLUICE_CNB_LIFECYCLE`, else `~/.local/cnb/lifecycle`), a wasi wicket beside it, then itself in a VM of that wicket, and in a VM each of two (`ha.md`: the deployment and its update). `demo/record.sh` re-records the README's demo video with VHS (`demo/README.md`)
- `sluice-wicket-runtime-firecracker` (Rust, own Cargo workspace): a tunnel client serving each route with Firecracker microVMs over vsock, VMs booted (`mode=boot`, `instances=N`), or clones of a snapshot (one per connection, reused, or pooled), within a VM / memory budget, reloaded from `--config`, the VMs' output on its stdout / stderr and a flume, their egress through it to the destinations a route allows (`egress.rs`); jail mode (`--jail-ids`, started as root) jails each VM (`jail.rs`) from a root keeper (`keeper.rs`) running the wicket unprivileged: keep the keeper single-threaded (it forks each VM's jail); `guest/` is the VMs' `/init` (musl, its own workspace: keep `guest/src/wire.rs` a copy of `src/wire.rs`), `scripts/cnb-rootfs.sh` turns an OCI / CNB image into a rootfs. Same gates (and the guest's); its VM test (`tests/vm.rs`) runs where `/dev/kvm` is usable (`sg kvm -c 'cargo test'` until the `kvm` group is in the login) and is skipped elsewhere, the CI's aarch64 runner among them (on an M3 or later Mac, `scripts/lima.sh` runs it on real aarch64, in a nested virtualization VM); `SLUICE_WICKET_RUNTIME_FIRECRACKER_JAIL=1` runs it jailed (through `sudo -n`). `--console` deploys uploaded rootfs images as routes, and apps (`console.rs`, `deployed.rs`), an OCI image's rootfs made on the wicket with `--guest` (`image.rs`, `rootfs.rs`), an app's one booted VM with a persistent disk (`disk.rs`: one writer, a `flock` going with its `firecracker`; a reload stops the old VM first). With `--guest` it stages source by Cloud Native Buildpacks too (`stage.rs`, the guest's `stage.rs`: a builder's `detector` and `builder` in a VM of the builder's image, no analyzer nor exporter, the droplet a tar laid over the run image by `PUT /api/images`): a guest change makes every builder's rootfs again. Never fork the wicket per VM (`vm.rs`: a fork holds its memory map lock); findings in `.kb/wicket-firecracker-findings.md`
- `sluice-wicket-oidc` (Rust, own Cargo workspace): the OpenID Provider client (discovery, the authorization code flow with PKCE, the claim rules, a session sealer) of the wickets' consoles and sluice-wicket-cf-api, with the mock provider their tests run (feature `mock`). Gates as sluice-flume's, with `--all-features`
- `sluice-wicket-console` (Rust, own Cargo workspace): what the consoles of sluice-wicket-runtime-wasi and sluice-wicket-runtime-firecracker share: the gate (token, OpenID sign-in, loopback only, no foreign origin), the server and the page's shared files (`console.css`, fonts, `kit.js` the scripts import; sluice-wicket-cf-api's `cf login --sso` pages wear the style too), the bodies (an upload streamed to a file under its digest), the directory's layout (`store`), an owner's writes refused below the highest epoch it sent (`fence`), what an apps' listing says of the wicket (`identity`: its id, flume node, build and budget), the long poll, the options. Same gates
- `sluice-wicket-keyvalue-gemfire` (Rust, own Cargo workspace): sluice-wicket-runtime-wasi's `gemfire` keyvalue store (a region of a Tanzu GemFire cluster through Tanzu GemFire for gRPC: the subset of `gemfire.v1.GemFire` it calls, `proto/`, so any service answering those methods serves it): the calls going round the servers (failing over only what may be sent twice, a swap only unsent), the locators' xDS (EDS `gemfire_grpc`), TLS / mTLS / a bearer token, and the mock cluster its and the wicket's tests run (feature `mock`; GemFire is proprietary: no test needs one); a production-like cluster's settings and findings in `.kb/wicket-keyvalue-gemfire.md`. Gates as sluice-flume's, with `--all-features`
- `sluice-wicket-registry` (Rust, own Cargo workspace): the OCI distribution client (references, manifests, blobs, registries' challenges) sluice-wicket-cf-api and sluice-wicket-runtime-firecracker pull images with. Same gates
- `sluice-wicket-server` (Rust, own Cargo workspace): what the listeners of sluice-wicket-runtime-wasi, sluice-wicket-runtime-firecracker and sluice-wicket-cf-api have alike: the accept loop with its connections' slots and TCP keepalive (`accept`), an HTTP/1.1 connection no client holds by going quiet (`http`). Same gates
- `sluice-wicket-tunnel` (Rust, own Cargo workspace): the tunnel client of sluice-wicket-runtime-wasi and sluice-wicket-runtime-firecracker (ListNodes fan-out, node sessions, per-connection flow control, the connection limit, the drain), their live access log's feed to a sluice-flume (`flume`), and their local mode's routing by host (`listener`); a wicket supplies its route table and how a connection is served (`routes::Table` / `routes::Binding`). Its test doubles (a tunnel server, a peer feeding the dispatch, a flume) are the wickets' too (feature `testing`). Gates as sluice-flume's, with `--all-features`
- `sluice-build-info` (Rust, own Cargo workspace): build script dependency of sluice-flume, sluice-wicket-runtime-wasi and sluice-wicket-cf-api embedding their build (git commit, dirty, build time; `SLUICE_GIT_COMMIT` where there is no work tree, as in the Docker builds). Same gates
- `sluice-example-upstream`: minimal sample upstream (`It works`, http/1.1 + h2c) for manual checks

The data plane relays raw bytes (the request head is inspected for routing; every request head gets the `X-Forwarded-*` headers, and with `rewrite-host=true` its host is rewritten on the wire). Honoring half-close (CLOSE frame) is essential for keep-alive / WebSocket passthrough.

## Conventions

- Coding standards: user-level skills (java-code-standards / spring-code-standards / java-package-structure / java-testing-standards). spring-javaformat validate is wired into the build.
- `application.properties`: keys in alphabetical order; a comment stays directly above the key it describes.
- gRPC 1.83.x quirks: `StreamObserver` / `ClientCallStreamObserver` live in `io.grpc.stub`. The client onReady handler may only be set inside `ClientResponseObserver#beforeStart`.
- Boot 4.1: `HealthIndicator` is in `org.springframework.boot.health.contributor`.
- wasmtime 50 (`sluice-wicket-runtime-wasi`; seen on 49): a timer raced inside the `run_concurrent` closure may never fire; put timeouts / watchdogs outside the call (see `supervise` in `wasm_host.rs`).
- Docker images via buildpack (`spring-boot:build-image`); no Dockerfile, except the Rust components (`sluice-flume/Dockerfile`, built from the repository root).
- Console: Mustache + htmx 4 (same setup as blog-frontend-htmx: vendored `htmx.min.js`, `{{#src}}` content-hashed URLs from `WebConfig`, `compression-maven-plugin` .br/.gz). htmx 4 inherits nothing implicitly (`:inherited`). The drawing geometry lives in `FlowDrawing`; templates stay logic-less.
- Native image (`-Pnative`, client/server): console view records are rendered via Mustache reflection -- when adding/renaming a record under `console/web`, register it in `sluice-server/src/main/resources/META-INF/native-image/am.ik.sluice/sluice-server/reflect-config.json`. Build args go in `META-INF/native-image/am.ik.sluice/<module>-netty/native-image.properties`: Spring AOT overwrites the one under `am.ik.sluice/<module>`. A downcall or upcall shape added to `Wasmtime` / `PluginInstance` goes in `sluice-client-netty/reachability-metadata.json` beside it. `./mvnw -pl sluice-client -am -PnativeTest test -Dtest=<class>` runs a test on a native image (CI runs `DirectBufferReleaseTest`, `ProxyWasmFilterTest` and `LlmUsageFilterTest` so).
- Tests that need a port before the server starts take it from `TestPorts.freePort()` (sluice-it), never by probing `new ServerSocket(0)` and closing it: the OS may hand that port out again.
- `sluice-it` classes run in 6 surefire forks at once (`-Dsluice.it.forks=N`), one class at a time per fork: a test must not depend on a quiet machine or on state outside its JVM (ports only via `TestPorts`, which reserves them across JVMs).
- Console E2E tests use Playwright (`ConsoleE2ETest`); the first run downloads Chromium. Launch it through `Chromium.launch` (sluice-it), never `playwright.chromium().launch()`: a browser that sees the host's interfaces fails a request with `net::ERR_NETWORK_CHANGED` when another fork's container starts or stops.
- Tests needing a flume run `sluice-flume` as a child process via `Flume.start()` (sluice-it), one per class; it exits with the JVM (stdin EOF).
- `.todo` numbers come from `.todo/claim-number.sh`.
