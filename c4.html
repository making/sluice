Level 3 — Components (data path)

General notes

  1. A single gRPC bidi stream multiplexes virtual TCP connections by conn_id. Frame types: DATA / CONNECT / CLOSE / ERROR / ADVERTISE / ADVERTISE_ACK / KEEP_ALIVE / MEMBERSHIP_UPDATE / DRAIN.
  2. The data plane relays raw bytes; only the request head is inspected (for routing), rewritten on the wire when preserve-host=false. Honoring half-close (CLOSE frame) keeps keep-alive / WebSocket passthrough transparent.
  3. Cluster: every client keeps one stream per node and each node holds the full route table (no shared store, no inter-node hop). DRAIN signals scale-down.
  4. Security: token / TLS (grpcs://, verification skip via sluice.insecure) / mTLS. Client certificates are issued by the console CA (sluice.ca-bundle).
  5. All blocking I/O runs on virtual threads; the sender side propagates backpressure into gRPC flow control via bounded queues + isReady().
  6. Level 4 (Code) is omitted on purpose: class-level diagrams would duplicate the source and go stale. For the code level, start from the relay core in sluice-proto — am.ik.sluice.tunnel (VirtualConnection / SessionSender / SocketRelay / StreamRelay / DuplexPipe / FrameWriter).
